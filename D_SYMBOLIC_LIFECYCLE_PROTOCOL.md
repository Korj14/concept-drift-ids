## 1. Purpose

This protocol freezes the symbolic treatment that distinguishes primary System D from matched
System C.

System C keeps accepted seed-matched R0.v2 frozen, including rule structure and rule confidence.

System D begins from that exact same R0.v2 but may publish later symbolic versions only through the
validated lifecycle defined here.

The operator is deliberately not "rebuild a tree and replace the rule base." Candidate generation,
independent validation, incumbent-staleness assessment, lifecycle resolution, conflict handling and
publication are separate stages with immutable evidence.

## 2. Primary causal sequence

For a drift-driven maintenance opportunity associated with shared neural child checkpoint
`theta_k`:

1. shared neural checkpoint `theta_k` is published under the frozen neural protocol;
2. candidate symbolic structures are generated from the neural transaction's fixed recent evidence;
3. the currently active D rule base remains in force;
4. an independent future validation block generated by `theta_k` is collected and allowed to
   mature;
5. current rules are evaluated for staleness on that validation block **before** any candidate can
   modify the active base;
6. candidates are evaluated on the same independent validation block;
7. lifecycle/redundancy/conflict policy is applied;
8. a new immutable rule-base version is published only if inference-relevant symbolic state changes;
9. the new version becomes effective at the next logical prediction at earliest.

No stage may use the known synthetic boundary, future observations or pending labels.

## 3. Symbolic transaction is tied to one neural checkpoint

Every symbolic maintenance transaction has one immutable `neural_checkpoint_sha256`.

Candidate generation, validation neural decisions and fidelity calculations all refer to that same
checkpoint.

If that checkpoint is superseded by a later shared neural publication before the required symbolic
validation block is complete:

- the symbolic transaction is closed as `superseded_before_validation`;
- no partial rule update is published;
- all already-generated candidates/evidence remain preserved for audit;
- the next maintenance transaction must use the newer checkpoint under its own evidence identity.

This prevents publication of a rule base that was validated to explain a neural model that is no
longer deployed.

## 4. Candidate-generation evidence

For primary D-drift, candidate generation uses exactly the 10,000-row **current-evidence window**
that produced the associated neural child checkpoint.

Those rows:

- were fully observed and label-mature before the neural transaction;
- are treatment-independent;
- have immutable row identities;
- are not the later symbolic-validation rows.

The updated child neural model is evaluated on those rows for explanation/rule mining.

Candidate generation is allowed to use evidence that participated in neural fine-tuning because it
is a proposal mechanism, not an acceptance test.

Candidate acceptance may **not** use those same rows.

## 5. Online feature attribution

The online candidate generator preserves the original R0 extraction family:

- SHAP DeepExplainer;
- raw attack logit;
- class-balanced background;
- class-balanced attribution sample;
- normalized global/benign/attack mean-absolute SHAP selection score;
- top 12 features.

### 5.1 Sampling

For the 10,000-row generation window:

- background target: up to 128 rows per true binary class;
- attribution target: up to 1,024 rows per true binary class;
- both samples are without replacement within their own sample operation;
- attribution count per class is `min(1024, available_class_rows)`.

At least 128 rows of each true class must exist to run candidate generation.

If either class has fewer than 128 rows:

- no new candidate structures are generated for that opportunity;
- the transaction may still perform incumbent staleness assessment once independent validation
  evidence is available;
- the event is logged as `candidate_generation_insufficient_class_evidence`;
- no class is oversampled or synthetically generated.

### 5.2 Deterministic seed namespace

For seed `s` and one-based symbolic maintenance opportunity `m`:

`symbolic_seed_base = 20261020 + 1000*s + 10*m`.

Use:

- background sampling: `base + 0`;
- attribution sampling: `base + 1`;
- surrogate tree random state: `base + 2`;
- validation bootstrap: `base + 3`.

The exact row identities of SHAP samples are persisted.

## 6. Online surrogate rule proposals

The child neural model is thresholded using the seed's already frozen System-A neural monitor
threshold to create the surrogate target.

This is the same neural-decision semantics used for R0 fidelity and avoids making the candidate
generator depend on D fused output.

The online surrogate is:

- `DecisionTreeClassifier`;
- criterion = gini;
- splitter = best;
- selected features = online top 12 SHAP features;
- target = updated child neural thresholded decision;
- equal-total-weight neural predicted classes;
- max_depth = 4;
- min_samples_leaf = 100;
- random_state = frozen event-specific surrogate seed.

The 100-row minimum leaf is an online proposal-granularity control for a fixed 10,000-row generation
window. It is **not** an acceptance criterion.

Candidate paths are canonicalized using the same deterministic bound-merging rules as R0.

### 6.1 Consequent semantics

Candidate consequent is the **weighted CART fitted leaf argmax**.

Unweighted majority among path rows is prohibited.

This explicitly preserves the corrected R0.v2 protocol semantics and prevents recurrence of the
historical R0.v1 implementation defect.

## 7. Independent online validation evidence

Candidate acceptance and incumbent lifecycle decisions use a new 10,000-row validation block.

Define:

`W_symbolic_validation = 10,000 rows`.

The validation block is the first 10,000 stream observations satisfying all of the following:

- predicted after publication of the transaction's child neural checkpoint;
- prediction actually produced by that child checkpoint;
- label becomes mature while that checkpoint remains the active shared neural state;
- row was not part of candidate-generation evidence.

The block is chronological, not randomly split from the candidate-generation window.

The active D rule base remains unchanged while this block is being collected.

### 7.1 Validation right-censoring

If the stream ends before all 10,000 validation rows mature, the symbolic response is
`right_censored_validation` and no partial publication is made.

If the neural checkpoint is superseded first, Section 3 applies.

### 7.2 Class-diversity requirement

Both binary classes must be present in the completed validation block.

If not, candidate acceptance and incumbent structural lifecycle changes are not executed. The
transaction is logged `insufficient_validation_class_diversity`.

No future rows are pulled backward to repair the block.

## 8. Online rule-quality quantities

Every candidate and every current/inactive rule considered for reactivation is evaluated on the same
completed validation block.

For consequent `c_r`:

- support = covered rows / 10,000;
- covered_count = number of covered validation rows;
- class_precision = fraction of covered rows with true class `c_r`;
- neural_fidelity = fraction of covered rows whose stored child-neural decision equals `c_r`;
- complexity = canonical antecedent condition count.

Neural fidelity uses the stored child-checkpoint decision under the fixed seed-specific System-A
neural threshold.

It does not use fused C/D decisions.

## 9. Sample-size-aware uncertainty gate

The static R0 requirement `covered_count >= 100` is **not** copied mechanically into the online
setting.

Online validation uses one-sided 95% Wilson lower confidence bounds for both class precision and
neural fidelity.

Use:

`z = 1.6448536269514722`.

For `k` successes in `n` covered observations, the one-sided Wilson lower bound is:

`LCB = (p_hat + z^2/(2n) - z*sqrt(p_hat*(1-p_hat)/n + z^2/(4n^2))) / (1 + z^2/n)`.

The online quality gate requires all of:

- support >= 0.001;
- covered_count >= 25;
- point class_precision >= 0.80;
- Wilson95-LCB(class_precision) >= 0.80;
- point neural_fidelity >= 0.90;
- Wilson95-LCB(neural_fidelity) >= 0.90;
- bootstrap full-gate persistence >= 0.90;
- complexity <= 4.

### 9.1 Why covered_count >= 25

At one-sided 95% confidence, fewer than 25 covered observations cannot establish a 0.90 lower bound
even with perfect observed neural fidelity.

Thus 25 is an uncertainty-derived minimum rather than a transferred static count.

At `n=25`, only perfect observed fidelity can clear the 0.90 LCB requirement; larger imperfect
samples require correspondingly stronger evidence.

## 10. Bootstrap stability

Use 100 stratified bootstrap replicates of the completed symbolic-validation block.

A bootstrap replicate counts as passing only if the rule satisfies the full online quantitative gate
for that replicate:

- support;
- covered count;
- point precision;
- precision Wilson lower bound;
- point fidelity;
- fidelity Wilson lower bound.

Complexity is invariant and checked outside the bootstrap.

Primary stability is the fraction of bootstrap replicates passing.

Acceptance requires stability >= 0.90.

Bootstrap random state uses the frozen `base + 3` seed.

## 11. Rule confidence

For an active rule that passes the online gate:

`confidence = min(point class_precision, point neural_fidelity)`.

This preserves accepted R0 confidence semantics.

Confidence is refreshed **only at completed symbolic maintenance opportunities** on independent
validation evidence.

There is:

- no per-row confidence update;
- no exponential decay;
- no update from pending labels;
- no confidence update from C/D fused outcomes.

Between symbolic publications, rule confidence is constant.

System C's accepted R0.v2 confidence values remain permanently frozen.

## 12. Staleness assessment precedes evolution

Before considering new candidate activation, every currently active D rule is scored on the completed
validation block.

Its pre-resolution status is recorded as:

- `valid`: passes the full online gate;
- `quality_failed`: sufficient coverage exists but one or more precision/fidelity/stability gates
  fail;
- `evidence_insufficient`: support/covered evidence is insufficient to validate the rule.

This staleness snapshot is immutable and is produced before candidate conflict/redundancy decisions.

A symbolic-recovery claim later requires this audit chain rather than merely showing that a newer rule
scores well.

## 13. Incumbent lifecycle state machine

Inference-active state is distinct from historical existence.

Primary current states:

- `active`;
- `demoted`;
- `retired`;
- `merged`;
- `refined_predecessor`.

Lifecycle transition labels include `retained` and `reactivated`.

### 13.1 Active rule passes

`active -> active` with transition `retained`.

Validation metrics/confidence are refreshed in the new rule revision.

Failure streak resets to zero.

### 13.2 Active rule fails

First consecutive failed completed validation opportunity:

`active -> demoted`.

Demoted rules are removed from predictive fusion but remain auditable and eligible for later
reactivation.

Failure streak becomes one.

### 13.3 Demoted rule passes

`demoted -> active` with transition `reactivated`.

The same semantic rule/lineage is restored with new validation evidence and refreshed confidence.

Failure streak resets to zero.

### 13.4 Demoted rule fails again

Second consecutive failed completed validation opportunity:

`demoted -> retired`.

Retirement does not delete history.

If the exact semantic rule later reappears and passes the full gate, it may be reactivated under the
same lineage with a new revision.

### 13.5 Retired rule passes later

`retired -> active` with transition `reactivated`, provided it survives the same redundancy and
conflict policy as any other accepted candidate/current rule.

### 13.6 Failed evidence and streaks

Both `quality_failed` and `evidence_insufficient` count as a failed completed opportunity for the
two-opportunity demotion/retirement state machine.

This is intentionally conservative: a rule that cannot be supported by recent independent evidence
does not retain predictive authority indefinitely.

Reactivation preserves the ability to recover recurring regimes.

## 14. Candidate semantic identity and exact-match handling

A semantic rule identity is a canonical hash of:

- seed;
- canonical antecedent;
- consequent.

If an accepted candidate has exact semantic identity with an existing historical rule:

- if that rule is already active and valid, the candidate is logged as
  `existing_semantic_identity` rather than creating duplicate structure;
- if the rule is demoted/retired and passes current validation, it is a reactivation candidate;
- lineage is preserved.

## 15. Same-class refinement and consolidation

The already frozen overlap coefficient is reused to avoid inventing unnecessary new similarity
scales.

### 15.1 Redundancy / merge-consolidation

Same-consequent activation overlap coefficient >= 0.95 is treated as strong redundancy.

The deterministic winner among candidate/current rules is selected by:

1. higher confidence;
2. higher support;
3. lower complexity;
4. lexicographically smaller semantic rule ID.

If a new candidate wins against one or more active redundant rules:

- the candidate becomes active;
- losing rules transition to `merged`;
- parent revision/lineage IDs are recorded;
- the operation is `merge_consolidation`.

If an incumbent wins, the redundant candidate is rejected.

No unvalidated synthetic union/intersection antecedent is constructed.

### 15.2 Refinement

For same-consequent overlap coefficient >= 0.50 and < 0.95, a candidate may be classified as a
refinement of the most-overlapping incumbent rule.

A candidate replaces the incumbent as a refinement only if:

- candidate passes the full online gate; and
- either candidate Pareto-dominates the incumbent on class precision, neural fidelity, support and
  complexity; **or**
- the incumbent's current staleness status is failed and the candidate passes.

The refined candidate inherits the incumbent lineage.

The predecessor becomes `refined_predecessor`.

If neither condition holds, the overlapping candidate is rejected as `no_refinement_gain` rather
than creating churn.

Ties in parent selection use larger overlap coefficient, then lexicographically smaller rule ID.

### 15.3 New addition

An accepted same-class candidate with overlap < 0.50 to every surviving same-class active rule is a
`new_addition` and receives a new lineage.

## 16. Cross-class conflict policy

Potential conflict requires opposite consequents and validation activation overlap coefficient >=
0.50, preserving accepted R0 semantics.

Use the existing Pareto comparison over:

- class precision;
- neural fidelity;
- support;
- complexity.

### 16.1 Incumbent dominates candidate

Candidate is rejected as `cross_class_dominated`.

### 16.2 Candidate dominates incumbent

Candidate may become active.

The dominated incumbent becomes demoted in the new version and retains its lineage/history.

### 16.3 Neither dominates

Both may remain/enter active state, but the relation is stored as
`unresolved_cross_class_conflict`.

At inference, any actual opposite-consequent coactivation causes symbolic abstention and neural
fallback under the already frozen runtime semantics.

The operator never forces a contradictory symbolic decision.

## 17. Existing-existing relation reevaluation

After staleness transitions and candidate integration, all surviving active rule pairs are rechecked
on the same validation block for:

- same-class redundancy;
- cross-class potential conflict.

The same deterministic policies apply.

This prevents the rule base from accumulating relations that were only checked when each rule first
entered.

## 18. Publication semantics

A maintenance attempt always produces an immutable maintenance-event artifact.

A **new rule-base version** is published only if inference-relevant symbolic state changes, including:

- active membership;
- rule antecedent/consequent;
- active confidence;
- conflict relation affecting abstention.

A pure no-op/rejection event with identical inference state records `no_rule_base_change` and keeps
the current version identity.

When published, the new version becomes effective at the next logical prediction at earliest.

No earlier prediction is recomputed.

Initial accepted R0.v2 rules retain their historical identity and receive a deterministic migration

### 19.1 Rule-base version identity

For seed `s`, successful D publications are numbered monotonically:

`d-s{s}-v0001`, `d-s{s}-v0002`, ...

Each version artifact stores:

- parent rule-base version/hash;
- maintenance-event ID;
- trigger/opportunity identity;
- neural checkpoint hash;
- active revision inventory;
- inactive lineage inventory;
- lifecycle decisions;
- canonical payload hash.

Files are write-once.

## 20. Rejected changes are first-class evidence

Every rejected candidate or lifecycle proposal is retained with:

- candidate/revision identity;
- generation evidence;
- validation evidence;
- all quality metrics;
- Wilson bounds;
- stability;
- overlap/conflict relations;
- explicit rejection reason.

Rejected rules are never silently discarded from the audit trail.

## 21. Symbolic recovery claim rule

The manuscript may call a rule/lineage "recovered" only when a documented chain exists:

1. earlier evidence showed the lineage/rule valid;
2. a later completed maintenance validation showed staleness/failure or demotion;
3. a subsequent accepted refinement/reactivation/replacement was published;
4. post-publication longitudinal evidence improved the relevant explanation outcome relative to the
   stale state.

A newly added rule with no demonstrated stale predecessor is an addition, not "recovery."

## 22. Symbolic transaction cost

Record separately:

- SHAP time;
- surrogate-fit time;
- validation waiting rows;
- candidate-validation time;
- lifecycle-resolution time;
- serialization time;
- active/historical rule counts;
- candidate count;
- accepted/rejected/refined/merged/demoted/retired/reactivated counts;
- conflict count;
- version size.

The scenario lacks trustworthy wall-clock arrival timestamps, so validation waiting is expressed in
logical rows while compute is reported as measured cost.

## 23. Treatment isolation

Primary System C:

- exact shared neural checkpoint trajectory;
- accepted R0.v2 remains structurally and numerically frozen;
- no confidence refresh;
- no lifecycle transition.

Primary System D:

- exact same shared neural checkpoint trajectory;
- symbolic state may change only through this operator.

Symbolic validation/evolution must not feed:

- detector input;
- replay admission;
- neural update evidence;
- neural optimizer;
- shared neural checkpoint selection;
- label availability.

## 24. Literature/novelty position

The operator is not claimed as the first adaptive rule system.

Adjacent work already establishes:

- online-updatable belief-rule IDS, including O-EBRB;
- online/chunk-based interpretable fuzzy-rule NIDS, including SPAFIS;
- broader concept-drift-aware adaptive NIDS;
- recent drift-triggered symbolic re-mining in adjacent cybersecurity/SOC settings.

The contribution remains the controlled conjunction of endogenous statistical trigger, validated
versioned lifecycle, matched neural control and longitudinal explanation evaluation.

The stricter generation/validation separation here is used to reduce optimistic self-validation; it
is not presented as a universal optimal online rule-learning algorithm.
